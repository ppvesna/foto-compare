## Цель

Продолжить постепенную миграцию к Architecture v2, не ломая рабочий сценарий сравнения.

## Шаг 1. Завершить references

1. Запустить ручную проверку: открыть старый эталон, выбрать его активным,
   создать и удалить новый эталон, перезагрузить браузер.
2. Запустить автотест в среде, где Flutter может записать в свой SDK cache.
3. Зафиксировать модуль отдельным коммитом.

## Реализованная структура references

Цель: собрать эталоны и калибровочные профили в одном владеющем модуле.

Структура:

```text
lib/features/references/
  domain/
    layout_profile.dart
    saved_reference.dart
  infrastructure/
    reference_storage.dart
    layout_profile_storage.dart
  references.dart
```

Соблюдённые ограничения:

- не менять `reference_profiles_v2` и `reference_profiles_active_id_v2`;
- не менять JSON `LayoutProfile`;
- не менять логику выбора активного эталона;
- не менять `CompareScreen`, кроме путей импорта;
- добавить тест загрузки старого JSON.

## Шаг 2. Модуль production

После `references` выделить:

- `ProductionJob`;
- `Sample`;
- нумер работы;
- нумер отпечатка;
- связь работы, эталона и протокола.

На первом шаге данные остаются локальными. Облачная схема не меняется в том же коммите.

## Отдельный rollout прав

1. Сделать backup Supabase и проверить миграцию на staging.
2. Проверить личные данные, организацию, чат, Storage и вход по нику.
3. Проверить 90-дневный Pro-grace для уже созданных аккаунтов.
4. Только после этого применить `005_access_control.sql` к production.

## Шаг 3. Фасад inspection

Только после `protocols`, `references` и `production` создать единый прикладной сценарий:

```text
RunInspection
```

Он будет координировать:

1. подготовку и совмещение;
2. предварительную карту;
3. геометрию;
4. коды;
5. OCR;
6. Lab ID;
7. точную Delta E;
8. сохранение протокола.

`CompareScreen` сначала будет вызывать фасад, а не разбираться на множество экранов и контроллеров.

## Порядок следующих платформенных модулей

1. `CloudStorage`: локальное хранение, Supabase Storage, затем Google Drive.
2. `DatabaseConnector`: подключение базы заказчика через server-side connector; пароль базы не попадает в web-клиент.
3. `AIProvider`: предварительная оценка и анализ результатов сравнения через заменяемый серверный адаптер.

Функционал сравнения можно отлаживать параллельно, потому что эти модули общаются с ним через контракты.

## Не входит в ближайший этап

- Полное переписывание `CompareScreen`.
- Замена Supabase.
- Разделение на микросервисы.
- Полное облачное хранение изображений.
- Реальный платежный провайдер и Enterprise-лицензии.
- PDF-отчёты.

## Критерий безопасности

Каждый шаг должен:

- сохранять старые локальные данные;
- не менять поведение UI;
- не менять алгоритм вместе с переносом;
- проходить анализ и веб-сборку;
- иметь отдельный понятный diff и коммит.
